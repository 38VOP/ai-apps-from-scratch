# ANCHOR — 3d-hub-aggregator

**Версія якоря:** 1.2
**Дата:** 15.08.2026
**Статус:** погоджено власником; оновлено правилом файлової модульності після Guardian-аналізу

## Мета

Агрегатор 3D-моделей (3ds Max) з підключених Telegram-каналів. Власник заходить у каталог, гортає категорії, відбирає моделі в кошик, зі свого кошика зберігає потрібне в іменовані проекти, а з проекту переходить у вихідний Telegram-пост для завантаження моделі. Окремо — двигун безпечного (анти-бан) парсингу підключених каналів і керована система категорій.

Будується з нуля. Наявні скріншоти чужого прототипу — лише візуальний референс стилю (темна тема, мінімалізм), не існуючий код і не джерело архітектурних рішень.

## Стек

- Backend: Python 3.11+, FastAPI, SQLAlchemy, SQLite
- Frontend: React 18, Vite, Lucide React
- Telegram клієнт: Telethon (async)
- Хостинг: локальний розвиток (uvicorn + vite dev server)

## Правило файлової модульності (додано Guardian, v1.2)

Модульність з розділу вище має бути відображена ФІЗИЧНО в структурі файлів, не лише в документації:

- Backend: кожен модуль — окремий файл/роутер (наприклад `backend/routers/cart.py`, `backend/routers/projects.py`, `backend/routers/catalog.py`, `backend/routers/categorize.py`, `backend/routers/sources.py`, `backend/routers/parser.py`, `backend/routers/admin.py`), `main.py` лише підключає роутери, не містить бізнес-логіки модулів напряму
- Frontend: кожен модуль — окремий компонент/файл (наприклад `frontend/src/components/Cart.jsx`, `Projects.jsx`, `Catalog.jsx`, `CategoryManager.jsx`, `SourcesPanel.jsx`, `AdminDashboard.jsx`), `App.jsx` лише компонує їх і тримає спільний стан навігації, не містить розмітку модулів напряму
- Мета: агент повинен мати змогу відкрити ОДИН файл модуля і працювати в ньому, не читаючи й не ризикуючи зачепити код інших модулів
- Поточний стан (виявлено Guardian 15.08.2026): НЕ виконано — `main.py` (612 рядків) і `App.jsx` (1752 рядки) містять усі модулі в одному файлі кожен. Потрібен окремий раунд рефакторингу до продовження нових фіч

## Функціональні вимоги

### MOD-SOURCES — Джерела
- Підключення довільної кількості Telegram-акаунтів (сесій), без штучного ліміту
- Підключення довільної кількості каналів-джерел, прив'язка канал↔акаунт
- Природний обмежувач — тільки flood-ліміти самого Telegram API на акаунт (звідси й ротація в MOD-PARSER)
- Заборонено автоматично створювати технічні/заглушкові акаунти без явного запиту власника і без явного позначення в UI, що це технічний запис, а не реальний акаунт

### MOD-PARSER — Парсинг-двигун (анти-бан пріоритет)
- Непомітність важливіша за швидкість — система сама вирішує темп, без ручних налаштувань власника
- Черга каналів на парсинг: новий канал не стартує миттєво
- Ротація серед підключених акаунтів, рандомізовані затримки між діями (без фіксованого крон-інтервалу)
- Два стани каналу:
  1. **Backlog** — початковий повний прохід історії каналу, з трекінгом прогресу (X з Y постів)
  2. **Monitoring** — після завершення backlog, тільки нові пости
- Автоматичне уповільнення/призупинення при наближенні до лімітів Telegram API
- **Заборонено генерувати демо/мокові/фейкові дані як заміну реального сканування**, у будь-якому вигляді. Якщо акаунт неавторизований/недоступний — статус "error" з поясненням, без запису жодних ModelItem
- Якщо канал прив'язаний до неавторизованого акаунта, а є інший авторизований — автопереприв'язка з попередженням власнику

### MOD-CATEGORIZE — Категорії, класифікація, прев'ю
- Список категорій керований власником (CRUD)
- Класифікатор при парсингу поста працює тільки з категоріями, активними на момент парсингу (позначені "зеленим" — див. нижче)
- Нова категорія застосовується лише до майбутніх постів, без ретроактивної перекласифікації
- Видалення категорії заборонено, поки в ній є моделі — спершу перенести/видалити моделі вручну, тільки тоді порожню категорію можна видалити
- Інтерфейс керування категоріями: кожна категорія — кольоровий чекбокс-перемикач (нейтральний/зелений/червоний). Зелений = активна для авто-класифікатора. Червоний = позначена на видалення. Кнопка "Застосувати": зелені зберігаються активними; червоні порожні видаляються; червоні непорожні НЕ видаляються — показати попередження з переліком категорій, які треба спершу розвантажити вручну
- Якщо пост містить кілька фото — автоматичний вибір найякіснішого як обкладинки (без ручного вибору при первинному парсингу)
- Ручні контролі постфактум на моделі: зміна категорії вручну; кнопка "Оновити прев'ю з джерела" (перезапускає авто-вибір обкладинки); кнопка "Видалити модель" — доступна завжди, незалежно від стану джерела (страхує зниклий канал/пост)

### MOD-CATALOG — Каталог і перегляд
- Картка моделі: фокус тільки на зображенні, метадані (движок, джерело, назва файлу) другорядні/приховані
- Класична пагінація: фіксована кількість прев'ю на сторінці + номери сторінок (offset/limit), без infinite scroll
- Лічильник моделей у категорії відповідає реальній кількості доступних записів
- Клік на модель у каталозі → додає в кошик (MOD-CART), не веде напряму в канал і не в проект

### MOD-CART — Кошик (тимчасовий буфер)
- Іконка кошика в шапці (справа) з лічильником
- Панель/сторінка кошика: сітка відібраних моделей з чекбоксом на кожній
- Дія "Очистити кошик" — повне видалення без збереження
- Дія "Зберегти відмічене у проект" — вибір існуючого Project або створення нового (з назвою); відмічені моделі переносяться в Project і зникають з кошика; невідмічені лишаються в кошику

### MOD-PROJECTS — Проекти (постійне сховище)
- Розділ "Проекти" — у лівому сайдбарі дашборду, одразу під списком категорій
- Сутність Project: id, назва (задає власник), дата створення, список моделей
- CRUD: створити (з назвою), перейменувати, видалити
- Можливість створити порожній проект напряму з сайдбару, без обов'язкової прив'язки до дій у кошику
- Модель потрапляє в Project через перенесення з кошика
- Модель зберігається безстроково, видаляється тільки вручну власником
- Клік на модель у проекті → відкриває вихідний Telegram-пост (deep link) для завантаження

### MOD-ADMIN — Адмінка/дашборд
- Статус кожного каналу: у черзі / backlog X% / monitoring
- Загальна статистика навантаження системи (активні задачі парсингу, розмір черги) — щоб власник бачив, коли безпечно додавати нові канали
- Проєктується з запасом на розширення — нові метрики/секції додаються без переробки існуючих екранів

## Скоуп — що НЕ входить

- Жодного функціоналу окрім: каталог, кошик, проекти, керування джерелами Telegram, парсинг-двигун, категорії
- Без соціальних фіч, без розширеної аналітики, без сповіщень
- Не ускладнювати процес вибору моделі додатковими кроками

## Дизайн

Мінімалізм, темна тема, акцент на зображеннях моделей, чистий інтерфейс без візуального шуму.
